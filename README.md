## ✨ 핵심 기능

| 기능 | 설명 |
| --- | --- |
| **의견 모으기 + 실시간 요약** | 회의 전 의견과 채팅을 현황판(공통 / 갈림 / 새로움 / 확인 필요 / 할 일)으로 정리하고, 긴 글은 요약 후 접습니다. |
| **AI 진행자** | 현황판 상태에 따라 의견 요청, 중간 정리, 투표 제안, 참여 독촉, 묻힌 질문 다시 꺼내기를 합니다. |
| **결론과 회의록** | [종료] 후 결정·할 일·미결·흐름을 정리한 결론 초안을 만들고, 관리자 승인 후 회의록으로 저장합니다. |

> AI는 정리하고 제안만 하며, 결정은 팀이 합니다.

## 🤝 백엔드 협업 규칙

### 1. 브랜치 전략

| 브랜치 | 용도 |
| --- | --- |
| `main` | 배포 가능한 브랜치 |
| `develop` | 개발 기준 브랜치 |
| `feature/기능명` | develop에서 생성 → 기능 개발 후 develop으로 병합 |
| `fix/수정내용` | develop에서 발생한 문제 수정 |
| `hotfix/수정내용` | main 배포 버전의 긴급 수정 |

기능 개발 완료 → PR 생성 → 리뷰 후 `develop` 병합 → 충분히 검증한 뒤 `develop`을 `main`에 병합합니다.

### 2. 병합과 코드 리뷰

- 직접 병합하지 않고 **PR을 통해서만** 병합합니다.
- PR 작성자는 변경 내용, 충돌 여부, 실행 가능 여부를 확인합니다.
- **최소 1명 이상 리뷰** 후 approve되면 병합합니다.
- 병합 방식은 **Rebase and merge**를 기본으로 하고, 병합된 작업 브랜치는 삭제합니다.
- 리뷰어는 코드 동작, 컨벤션 준수, 불필요한 코드 여부를 확인합니다.
- 코멘트에는 수정이 필요한 이유를 함께 적고, 공격적인 표현은 피합니다.

#### 리뷰 코멘트 표시

| 표시 | 의미 | 리뷰 제출 |
| --- | --- | --- |
| 👍 | 칭찬 | Approve |
| ❗ | 필수 수정 요청 | 하나라도 있으면 Request changes |
| ❓ | 이해가 어려운 부분 질문 | 답변이 결과에 영향을 주면 Comment, 그 외 Approve |
| 💊 | 필수는 아닌 개선 제안 | Approve |
| 💬 | 의견·참고 사항 공유 | Approve |

### 3. 커밋 컨벤션

형식: `type: 커밋 내용` (예: `feat: 로그인 기능 구현`, `fix: 회원가입 유효성 검사 오류 수정`)

| 타입 | 용도 |
| --- | --- |
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 의미 변화 없는 포맷 수정 |
| `refactor` | 기능 변경 없는 구조 개선 |
| `chore` | 빌드, 패키지, 기타 설정 |
| `test` | 테스트 코드 추가·리팩토링 |

본문은 선택이며, 필요하면 무엇을 왜 바꿨는지 간단히 적습니다.

### 4. PR · 이슈 작성

PR 제목은 커밋과 같은 형식인 `type: 작업 내용`을 사용합니다. (예: `feat: 로그인 API 구현`)

### 5. 아키텍처와 코드 스타일

**Controller → Service → Repository** 3계층 구조를 기본으로 사용합니다. (프로젝트 진행에 따라 팀 논의로 변경 가능)

| 계층 | 역할 | 예시 |
| --- | --- | --- |
| Controller | HTTP 요청 수신, 입력 검증, 응답 반환 | `UserController` |
| Service | 비즈니스 로직, 트랜잭션 처리 | `UserService` |
| Repository | 데이터 조회·저장 | `UserRepository` |

#### 네이밍

클래스는 PascalCase, 메서드·변수는 camelCase, 상수는 UPPER_SNAKE_CASE를 사용합니다.

| 구분 | 형식 | 예시 |
| --- | --- | --- |
| Entity | 도메인명 | `User` |
| 요청 DTO | 동작 + 도메인명 + Request | `CreateUserRequest` |
| 응답 DTO | 도메인명 + Response | `UserResponse` |
| 예외 | 상황 + Exception | `UserNotFoundException` |
| 메서드 | 동사 + 대상 | `createUser`, `getUser` |
| 상수 | 대문자 + 언더스코어 | `MAX_LOGIN_ATTEMPT` |

#### 그 외

- 패키지는 역할별로 `controller`, `service`, `repository`, `entity`, `dto` 등으로 구분합니다.
- 코드 포맷은 IntelliJ 기본 포맷을 따릅니다.
- 불필요한 주석은 쓰지 않고, 이해하기 어려운 로직에만 간단히 설명을 남깁니다.
- 사용하지 않는 import와 코드는 커밋 전에 정리합니다.
